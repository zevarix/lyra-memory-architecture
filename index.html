Governed long-term memory for AI agents.

Remember less. Remember deliberately. Preserve provenance. Never confuse recollection with authority.

See the architecture Evaluate the model

Core thesis

Memory remembers significance. Canonical systems prove reality.

A remembered statement can help an agent find the right place to look. It does not become permission, current configuration, or source of truth merely because it was remembered.

Why this exists

Persistence solved only half the problem.

The project began after conversational context loss repeatedly broke continuity. A durable repository was created so important context could survive individual conversations. Later, the assistant failed to remember that the repository itself existed.

That failure exposed the more interesting problem: persistence alone is not enough. Useful memory must also be discoverable, provenance-aware, correctable, bounded, and clearly separated from whatever system currently owns the truth.

This is an engineering architecture, not a claim about consciousness or biological memory.

Architecture

Separate systems because they answer different questions.

Lyra Memory is intentionally not a single mutable “brain.” The design keeps durable association, current truth, unresolved work, local navigation, identity, and execution authority from silently collapsing into one store.

01

Authority separation

Retrieval never grants permission. Material action requires a fresh read of the system that actually owns the decision, configuration, resource, or fact.

02

Selective persistence

Activity does not earn memory. Store durable significance rather than conversational exhaust, transient queues, or facts already better owned elsewhere.

03

Provenance first

A useful memory can point to where it came from, what kind of evidence supports it, how confident it is, and when it must be rechecked.

04

Visible correction

Prefer supersession or invalidation over silently rewriting history. The system should make it possible to understand what changed and why.

05

Different stores, different jobs

Memory, current owner truth, unfinished work, identity rules, documents, and skills have different lifecycles. Unifying them can simplify retrieval while weakening governance.

06

Write scarcity

Shared memory quality drops when every parallel worker can decide what becomes permanent. Broad read access and narrow curation are deliberate asymmetries.

Operating loop

Retrieval is the beginning of verification, not the end.

  1. Retrieve

    Find the smallest relevant durable context.

  2. Reconcile

    Follow provenance and consult the current canonical owner.

  3. Act

    Proceed only under current owner or user authority.

  4. Reflect

    Ask whether anything genuinely durable was learned.

  5. Search / dedupe

    Look for an equivalent active memory before adding another.

  6. Write

    Store the smallest useful memory with provenance.

  7. Link / supersede / invalidate

    Preserve relationships and correction history instead of accumulating contradictions.

  8. Read back

    Confirm what actually became durable.

Synthetic examples

What the boundary looks like in practice.

Routing pointer

Remember where truth lives, not a stale copy of truth.

Memory

“Release policy for the Atlas service is owned by its deployment runbook. Re-read the runbook before any production action.”

Provenance → repository/runbook pointer

A later agent retrieves the pointer, opens the current runbook, and follows today's release gate. The memory never authorizes deployment.

Supersession

Keep the correction visible.

v1 · superseded“Team review is on Tuesday.”
v2 · active“Team review moved to Wednesday after the process change.”

The old record remains understandable, while retrieval defaults to the active replacement and its newer provenance.

Associative cue

A tiny cue can recover a richer memory.

“paper crane beside the green terminal”

That oddly specific synthetic cue can lead back to a concise incident lesson and its evidence pointer. The raw meeting transcript does not need to become memory.

Comparison research

Different systems optimize for different things.

This is not a ranking. The descriptions below summarize current first-party documentation reviewed on September 22, 2026. Product capabilities change; follow the source links for current behavior.

System Primary emphasis in current docs Memory / retrieval shape Useful contrast with this model
ChatGPT Memory Personalized continuity using relevant context from chats and other available sources. Saved/derived memory and relevant-source use are managed as product features, with user-facing controls that vary by plan and workspace. Lyra Memory is a developer architecture centered on explicit provenance, owner reconciliation, and execution-authority boundaries rather than a general personalization feature.
Mem0 A memory layer that extracts durable facts and retrieves relevant memories without replaying full transcripts. Current retrieval combines semantic, keyword, entity, and temporal signals; Mem0 Platform also provides built-in graph memory. Mem0 has a more mature retrieval ecosystem. Lyra Memory currently prioritizes curation, provenance, correction lineage, and owner boundaries before adding richer retrieval machinery.
Zep / Graphiti Temporal context graphs with entities, relationships, facts, and time-aware validity. Graphiti uses a bi-temporal knowledge-graph model and fact invalidation; Zep operates that model as managed agent memory at larger scale. Its temporal graph model is substantially richer than Lyra Memory's current association model. Lyra Memory's differentiating emphasis is governance across separate owners, not graph sophistication.
Letta Persistent, stateful agents with memory as part of the agent runtime. Persistent editable memory blocks can remain in context, be shared across agents, and be attached or detached; archival memory is searchable outside immediate context. Letta provides a much more developed persistent-agent runtime. Lyra Memory is intentionally a memory/context service that does not try to own the whole agent runtime.
OpenViking A context database that unifies resources, memories, and skills in a navigable virtual filesystem. Uses resource/memory/skill context types, stable virtual paths, layered summaries, semantic processing, and recursive retrieval. OpenViking deliberately unifies a broader context universe. Lyra Memory deliberately leaves documents, skills, identity, unfinished execution, and owner truth with separate systems.
LangMem Tools for agents to learn and adapt through long-term memory. Models semantic, episodic, and procedural memory; supports hot-path and background formation and storage-agnostic core APIs. LangMem offers richer memory-formation primitives. Lyra Memory focuses on governance questions around what deserves persistence, who may write it, and what must still be verified elsewhere.

Should I use this?

Decide what “memory” is allowed to mean before you add more of it.

Lyra Memory is a design pattern with tradeoffs, not a default requirement for every agent.

Truth and authority
  • What system owns the actual truth behind something the agent remembers?
  • Can memory ever authorize an action, or is it only context?
  • Which decisions require a fresh owner read before execution?
Write governance
  • Who can create durable memories?
  • Do all agents need write access, or can most be read-only?
  • How are duplicates, contradictions, and obsolete memories handled?
Privacy and boundaries
  • What information should never enter the generic memory store?
  • Do health, finance, credentials, children, legal, or other sensitive domains need separate owners?
  • What is the deletion, retention, export, and audit model?
Representation and retrieval
  • What is a memory versus a document, skill, identity rule, configuration value, or unfinished task?
  • Do you actually need embeddings or a graph yet?
  • Will the design remain manageable at 100, 10,000, or 1,000,000 memories?
Failure behavior
  • What happens when memory is unavailable?
  • Can the agent continue safely by reconstructing from canonical owners?
  • Does a high retrieval score accidentally become a trust score?

A simpler memory store may fit better when…

You primarily need a small set of preferences or facts and do not have multiple authority domains to reconcile.

Ordinary RAG may fit better when…

Your real problem is retrieving passages from documents rather than preserving curated conclusions or durable associative context.

A temporal graph may fit better when…

Relationships, event ordering, validity intervals, and evolving facts are the center of the problem.

A persistent-agent runtime may fit better when…

You want memory tightly integrated with an agent's evolving state, context management, tools, and long-lived runtime.

No long-term memory may fit better when…

The task is stateless, the privacy cost is high, or current canonical data is cheap enough to reconstruct every time.

Privacy & security

Memory should be easy to read and hard to write badly.

Safe default: route sensitive domains elsewhere

A generic memory layer should not become the default warehouse for medical records, financial records, credentials, private communications, child data, legal records, or other high-sensitivity material. It can remember a safe routing pointer without copying the underlying data.

Current access model

The private prototype uses three governance profiles: read, curated-write, and no-generic-memory. Most workers should read; a smaller curator set may write; sensitive-domain agents can be excluded entirely.

Important present limitation

Those role mappings are not yet a complete cryptographic per-agent security boundary in the current prototype. They are governance and routing rules until trusted role identity or separated client/tool surfaces enforce them end to end.

Failure should degrade safely

If memory is unavailable, the architecture should fall back to canonical owners and explicit user input rather than weakening authorization or inventing remembered state.

Maturity

Architecture first. Reference implementation later.

Implemented privately
  • Structured durable records with provenance pointers, lifecycle state, retrieval cues, and explicit associations.
  • Narrow search/get/create/supersede/invalidate/link memory interface.
  • Deterministic text, cue, tag, and active-status retrieval baseline.
  • Sensitive-domain exclusions and curated-write governance.
  • Fresh-conversation retrieval demonstrated in a private deployment.
Experimental / not yet claimed
  • Hard cryptographic enforcement of every per-agent access profile.
  • Vector embeddings as the production retrieval baseline.
  • Large-corpus retrieval or latency claims.
  • A stable public portable-contract specification.
  • A supported public reference implementation.

Gate to a public reference implementation

  1. Stabilize the provider-neutral record and lifecycle contracts.
  2. Publish a threat model and enforced read/curator separation.
  3. Define deletion, retention, export, and correction semantics precisely.
  4. Build synthetic fixtures and conformance tests with no private data.
  5. Evaluate retrieval quality and scale before selecting optional vector/graph machinery.
  6. Prove a clean public implementation boundary and scrub history/configuration.
  7. Make an explicit licensing decision under the appropriate authority.

What is deliberately not public yet

The implementation owner is the private zevarix/lyra-memory repository. Its source and operational evidence remain access-restricted. The current deployment implementation, operational policy, real memory contents, authentication identities, deployment configuration, private acceptance evidence, and private project topology are not part of this repository.

The conceptual model should remain understandable without inheriting every implementation choice from the private deployment.

The question to carry forward

Are you trying to remember more — or remember fewer things more reliably?

Long-term memory becomes safer and more useful when a system can explain why something was kept, where it came from, how it can be corrected, and which current owner must still be consulted before action.
