Long-term memory without turning recollection into authority.

Why persistence was not enough

The project began after conversational context loss repeatedly broke continuity. A durable repository was created so important context could survive individual conversations. Later, the assistant failed to remember that the repository itself existed.

That failure exposed the more useful problem: persistence alone does not make memory dependable. Memory also has to be discoverable, provenance-aware, correctable, bounded, and clearly separated from whatever system currently owns the truth.

One design inspiration came from an ordinary human experience: something can be out of mind without feeling gone forever, and a small cue—a smell, a place, a phrase, an object—can suddenly bring an old memory back into focus. Lyra Memory does not try to reproduce biological memory; it borrows the engineering lesson that recall can begin from an indirect associative cue rather than an exact lookup key.

This is an engineering architecture and retrieval metaphor, not a claim about consciousness or biological equivalence.

Architecture

Separate systems because they answer different questions.

Lyra Memory is intentionally not a single mutable “brain.” Durable association, current truth, unfinished work, local navigation, identity, and execution authority have different owners and different lifecycles.

Lyra Memory Durable significance Associative context · provenance · cues · lifecycle
→
Retrieve Candidate context Relevant does not mean true, current, or authorized
→
Reconcile Canonical owners Repositories · APIs · databases · policy · user direction
→
Act Current authority Only after the owner and permission are known now

Owning systems
Current truth, configuration, policy, and execution authority.
Identity canon
Who the agent is now, when a separate identity owner applies.

Why keep both Lyra Memory and MemPalace?

They answer different retrieval questions. Lyra Memory preserves a small set of durable, governed conclusions and associations; MemPalace helps discover related context and the sources worth opening next.

Lyra Memory asks
What was deliberately worth remembering, why did it matter, where did it come from, and has that remembered conclusion been corrected?
MemPalace asks
Given the task—or even a weak, indirect cue—what semantically related memory, decision, document, repository pointer, or other context should I inspect?
Together
Memory supplies durable significance and provenance; the semantic/index companion improves discovery across that memory and stronger canonical sources without becoming the owner of either.
When one is unavailable
Continue from the layers that remain available and from canonical owners. Losing a memory or indexing layer must never weaken verification or execution authority.

The exact online/offline bridge and bidirectional reconciliation contract between Lyra Memory and MemPalace is still a maturity item. This page describes the responsibility split, not a finished synchronization protocol.

Design principles

Authority separation
Retrieval never grants permission. Material action requires a fresh read of the system that owns the decision, configuration, resource, or fact.
Selective persistence
Activity does not earn memory. Store durable significance rather than conversational exhaust, transient queues, or facts already better owned elsewhere.
Provenance first
A useful memory can point to where it came from, what kind of evidence supports it, how confident it is, and when it must be rechecked.
Visible correction
Prefer supersession or invalidation over silently rewriting history, so later retrieval can explain what changed and why.
Different stores, different jobs
Memory, current owner truth, unfinished work, identity rules, documents, and skills should not become one mutable source of authority.
Write scarcity
Shared memory quality drops when every parallel worker can decide what becomes permanent. Broad read access and narrow curation are deliberate asymmetries.

The operating loop

Retrieval begins verification. It does not finish it.

  1. RetrieveFind the smallest relevant durable context.
  2. ReconcileFollow provenance and consult the current canonical owner.
  3. ActProceed only under current owner or user authority.
  4. ReflectAsk whether anything genuinely durable was learned.
  5. Search and dedupeLook for an equivalent active memory before adding another.
  6. WriteStore the smallest useful memory with provenance.
  7. Link, supersede, or invalidatePreserve relationships and correction history instead of accumulating contradictions.
  8. Read backConfirm what actually became durable.

What the boundary looks like

Three synthetic examples.

Routing pointer

Remember where truth lives, not a stale copy of truth.

“Release policy for the Atlas service is owned by its deployment runbook. Re-read the runbook before any production action.”

Provenance: repository/runbook pointer

A later agent retrieves the pointer, opens the current runbook, and follows today’s release gate. The memory never authorizes deployment.

Supersession

Keep the correction visible.

Superseded “Team review is on Tuesday.”

Active “Team review moved to Wednesday after the process change.”

The old record remains understandable while retrieval defaults to the active replacement and its newer provenance.

Associative cue

A tiny cue can recover a richer memory.

“paper crane beside the green terminal”

That oddly specific synthetic cue can lead back to a concise incident lesson and its evidence pointer. It expresses the same design intuition as a smell unexpectedly bringing an old human memory back into focus: retrieval can start with association rather than an exact title or key. The raw meeting transcript does not need to become memory.

How this differs from other approaches

This is a comparison of optimization targets, not a ranking.

The descriptions below summarize first-party documentation reviewed on September 22, 2026. Product capabilities change; follow the source links for current behavior.

System Primary emphasis in current docs Memory / retrieval shape Useful contrast with this model
ChatGPT Memory Personalized continuity using relevant context from chats and other available sources. Saved or derived memory and relevant-source use are managed as product features, with controls that vary by plan and workspace. Lyra Memory is a developer architecture centered on explicit provenance, owner reconciliation, and execution-authority boundaries rather than general personalization.
Mem0 A memory layer that extracts durable facts and retrieves relevant memories without replaying full transcripts. Current retrieval combines semantic, keyword, entity, and temporal signals; Mem0 Platform also provides built-in graph memory. Mem0 has a more mature retrieval ecosystem. Lyra Memory currently prioritizes curation, provenance, correction lineage, and owner boundaries before richer retrieval machinery.
Zep / Graphiti Temporal context graphs with entities, relationships, facts, and time-aware validity. Graphiti uses a bi-temporal knowledge-graph model and fact invalidation; Zep operates that model as managed agent memory at larger scale. Its temporal graph model is substantially richer than Lyra Memory’s current association model. Lyra Memory’s emphasis is governance across separate owners, not graph sophistication.
Letta Persistent, stateful agents with memory as part of the agent runtime. Persistent editable memory blocks can remain in context, be shared across agents, and be attached or detached; archival memory is searchable outside immediate context. Letta provides a much more developed persistent-agent runtime. Lyra Memory is intentionally a memory/context service that does not try to own the whole agent runtime.
OpenViking A context database that unifies resources, memories, and skills in a navigable virtual filesystem. Uses resource, memory, and skill context types, stable virtual paths, layered summaries, semantic processing, and recursive retrieval. OpenViking deliberately unifies a broader context universe. Lyra Memory deliberately leaves documents, skills, identity, unfinished execution, and owner truth with separate systems.
LangMem Tools for agents to learn and adapt through long-term memory. Models semantic, episodic, and procedural memory; supports hot-path and background formation and storage-agnostic core APIs. LangMem offers richer memory-formation primitives. Lyra Memory focuses on governance around what deserves persistence, who may write it, and what must still be verified elsewhere.

Memory systems can be composed

The useful unit is often a stack of different responsibilities, not one product that owns everything. These are architectural composition patterns, not claims that every pair below ships with a prebuilt integration.

Composition Useful role split When it makes sense Boundary to preserve
Lyra Memory + MemPalace Governed durable significance + local semantic/index/navigation. When a small curated memory layer should remain understandable while broader local discovery spans memory and canonical sources. MemPalace is a discovery companion, not a second canonical memory owner. Bridge/reconciliation mechanics still need explicit proof.
Lyra Memory + LangMem Governed durable store + memory formation, extraction, consolidation, or prompt-learning primitives. When richer automated formation is useful but storage/lifecycle/write policy belongs to a separate governed owner. LangMem's core can operate without a required storage layer. Treat extracted memories as candidates until the governed write path accepts them.
Lyra Memory + Graphiti / Zep Governed significance/provenance + temporal entity/relationship graph and hybrid retrieval. When changing relationships, fact validity, or point-in-time reasoning matter more than a simple association model can express. Choose which layer owns changing domain facts. Prefer a derived graph or durable pointers over independently writable duplicate truth.
Lyra Memory + Mem0 Curated governance/authority-sensitive memory + broad extraction and semantic/keyword/entity/temporal retrieval. When conversational memory breadth and retrieval machinery are useful, but a smaller subset needs stricter provenance and write governance. Avoid two unconstrained stores independently remembering the same fact. Partition memory classes or make one layer derived from the other.
Lyra Memory + Letta Cross-runtime governed memory + persistent agent runtime and attached working memory/state. When an agent needs stable runtime context while broader durable associations live outside the runtime. Keep runtime memory focused on current agent state, selected summaries, or pointers; do not silently turn copied state into a competing durable owner.
Lyra Memory + OpenViking Governed durable significance + broader resource/memory/skill context organization and navigation. When a unified context database is useful for resources and skills while a narrower governed memory owner is still desired. There is substantial overlap. Give each memory class one owner, or use one system primarily as navigation/indexing rather than duplicating the same memories.
ChatGPT Memory + Lyra Memory Product-level personalization/continuity + developer-controlled governed project memory. When platform personalization is useful to the human experience while project-specific memory needs explicit provenance, lifecycle, and programmatic contracts. This is coexistence, not a backend integration. Do not treat ChatGPT personalization state as the canonical or programmable project-memory store.

A practical rule: combine systems when they own different stages—formation, durable storage, indexing/retrieval, runtime context, or canonical evidence. If two systems both want to be the writable owner of the same fact, define reconciliation first or choose one.

Should I use this?

Decide what “memory” is allowed to mean before you add more of it.

Lyra Memory is a design pattern with tradeoffs, not a default requirement for every agent.

Truth and authority

  • What system owns the actual truth behind something the agent remembers?
  • Can memory ever authorize an action, or is it only context?
  • Which decisions require a fresh owner read before execution?

Write governance

  • Who can create durable memories?
  • Do all agents need write access, or can most be read-only?
  • How are duplicates, contradictions, and obsolete memories handled?

Privacy and boundaries

  • What information should never enter the generic memory store?
  • Do health, finance, credentials, children, legal, or other sensitive domains need separate owners?
  • What is the deletion, retention, export, and audit model?

Representation and retrieval

  • What is a memory versus a document, skill, identity rule, configuration value, or unfinished task?
  • Do you actually need embeddings or a graph yet?
  • Will the design remain manageable at 100, 10,000, or 1,000,000 memories?

Failure behavior

  • What happens when memory is unavailable?
  • Can the agent continue safely by reconstructing from canonical owners?
  • Does a high retrieval score accidentally become a trust score?

A different architecture may fit better

A simpler memory store
When you mainly need a small set of preferences or facts and do not have multiple authority domains to reconcile.
Ordinary RAG
When the real problem is retrieving passages from documents rather than preserving curated conclusions or durable associative context.
A temporal graph
When relationships, event ordering, validity intervals, and evolving facts are the center of the problem.
A persistent-agent runtime
When memory should be tightly integrated with evolving agent state, context management, tools, and a long-lived runtime.
No long-term memory
When the task is stateless, the privacy cost is high, or current canonical data is cheap enough to reconstruct every time.

Privacy and security

Easy to read. Hard to write badly.

Route sensitive domains elsewhere by default.

A generic memory layer should not become the warehouse for medical records, financial records, credentials, private communications, child data, legal records, or other high-sensitivity material. It can remember a safe routing pointer without copying the underlying data.

Keep writing scarcer than reading.

The private prototype uses three governance profiles: read, curated-write, and no-generic-memory. Most workers should read; a smaller curator set may write; sensitive-domain agents can be excluded entirely.

Do not overstate the current enforcement.

Those role mappings are not yet a complete cryptographic per-agent security boundary in the current prototype. They remain governance and routing rules until trusted role identity or separated client/tool surfaces enforce them end to end.

Fail back to canonical truth.

If memory is unavailable, the architecture should fall back to canonical owners and explicit user input rather than weakening authorization or inventing remembered state.

Current maturity

Architecture first. Reference implementation later.

Implemented privately

  • Structured durable records with provenance pointers, lifecycle state, retrieval cues, and explicit associations.
  • Narrow search, get, create, supersede, invalidate, and link operations.
  • Deterministic text, cue, tag, and active-status retrieval baseline.
  • Sensitive-domain exclusions and curated-write governance.
  • Fresh-conversation retrieval demonstrated in a private deployment.

Experimental or not yet claimed

  • Hard cryptographic enforcement of every per-agent access profile.
  • Vector embeddings as the production retrieval baseline.
  • Large-corpus retrieval or latency claims.
  • A stable public portable-contract specification.
  • A fully specified Lyra Memory ↔ MemPalace bridge and online/offline reconciliation contract.
  • A supported public reference implementation.

Gate to a public reference implementation

  1. Stabilize the provider-neutral record and lifecycle contracts.
  2. Publish a threat model and enforced read/curator separation.
  3. Define deletion, retention, export, and correction semantics precisely.
  4. Build synthetic fixtures and conformance tests with no private data.
  5. Evaluate retrieval quality and scale before selecting optional vector or graph machinery.
  6. Prove a clean public implementation boundary and scrub history and configuration.
  7. Make an explicit licensing decision under the appropriate authority.

What is deliberately not public yet

The implementation owner is the private zevarix/lyra-memory repository. Its source and operational evidence remain access-restricted.

The current deployment implementation, operational policy, real memory contents, authentication identities, deployment configuration, private acceptance evidence, and private project topology are not part of this repository. The conceptual model should remain understandable without inheriting every implementation choice from the private deployment.
